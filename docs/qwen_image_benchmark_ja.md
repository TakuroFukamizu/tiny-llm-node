# ベンチマーク — sd.cpp vs ComfyUI(Qwen-Image-2.1 / Pi 5 + RTX 4060)

**Language:** [English](qwen_image_benchmark.md) | 日本語

このノードの2つの画像生成経路の生成時間を直接比較する:

- **stable-diffusion.cpp**(Vulkan)+ **unsloth 4bit GGUF** — 推奨経路
  ([image_generation_qwen_image_ja.md](image_generation_qwen_image_ja.md))。
- **ComfyUI int8**(`comfy_kitchen`, CUDA)+ **int8 safetensors** — ノードUI経路
  ([付録A](image_generation_qwen_image_ja.md#付録a--comfyui-int8-経路検証済み))。

> これは**時間**の比較。両経路は量子化方式が異なる(4bit GGUF vs int8)ため出力は
> 完全一致しない。この設定では品質は同等だが、本書の主題ではない。

## 結論(1行)

- **1つのプロンプトで反復(seedを変える):** ComfyUI **ウォーム**が圧勝 —
  **~8〜18秒** vs sd.cpp **~150〜170秒**。ComfyUIがテキスト条件付けをキャッシュし、
  サンプラーのみ再実行するため。
- **毎回違うプロンプト(一般的)または単発:** **sd.cpp が有利** —
  **~148〜170秒** vs ComfyUI **~232〜240秒**。ComfyUI の int8 重み(6.8 + 8.8 GB)は
  8GB VRAM を超過し、新プロンプトごとに 8.8GB のテキストエンコーダを再ロード/スワップ
  するため。sd.cpp の軽い 4bit ロードの方が1枚あたり安い。
- **Edit:** sd.cpp は動作(**~166秒**)、ComfyUI int8 の Edit は**クラッシュ**
  (cuDNN / KSampler)。既知の CUDA 不安定と一致。

## 方法

- ノード: Pi 5(8GB)+ RTX 4060(8GB)、90W キャップ、CUDA ツールキット無し。
- 全ラン共通: **512×512, cfg 2.5, euler / simple**。T2I は 8・20 step、I2I は
  10 step・denoise 0.6、Edit は 10 step。I2I/Edit は同一の 512×512 初期画像を使用。
- sd.cpp は `sd-cli`(1枚ごとに1プロセス=毎回モデル再ロード)。
- ComfyUI は常駐サーバへ HTTP API(モデルは呼び出し間で保持)。投入〜完了の実時間。
- 全体を通して `boot_id` を監視 — この設定では**どちらの経路も #2 瞬断なし**。
- 小サンプル(多くのセルで n=2)。±1秒ではなくオーダーで見ること。

### 方法を決めたキャッシュの注意

ComfyUI はグラフと seed が完全一致すると**キャッシュ結果**(~2秒)を返す(本物の
生成ではない)。そこで ComfyUI のウォームは2通りで計測した: **(a) 同一プロンプト・
seed のみ変更**(テキスト条件付けはキャッシュされ、サンプラーのみ再実行)と
**(b) 毎回新しいプロンプト**(テキストエンコーダを再実行)。両者は全く異なるため、
どちらも報告する。

## 数値(512×512)

### ComfyUI int8(CUDA, 常駐サーバ)

| モード | step | コールド(初回・ロード込) | ウォーム(同一prompt, seed変更) | ウォーム(新prompt) |
|---|---|---|---|---|
| T2I | 20 | 232秒 | **14〜18秒** | ~232秒 |
| T2I | 8 | — | **8秒** | **236秒**(×2) |
| I2I | 10 | — | — | **240秒** |
| Edit | 10 | — | — | **失敗**(`exec_error:KSampler`, cuDNN) |

### sd.cpp 4bit GGUF(Vulkan, `sd-cli` — 毎回再ロード)

| モード | step | Run 1 | Run 2 |
|---|---|---|---|
| T2I | 20 | 168.6秒 | 172.8秒 |
| T2I | 8 | 148.2秒 | 147.1秒 |
| I2I | 10 | 146.6秒 | — |
| Edit | 10 | 166.4秒 | — |

### sd.cpp の時間の内訳(`sd-cli` 1回, 8-step T2I ≈ 148秒)

| フェーズ | 時間 | 備考 |
|---|---|---|
| テキストエンコーダ ロード+エンコード | ~70秒 | Qwen3-VL は **CPU** 実行(paramsはCPU/RAM) |
| 拡散モデル ロード | ~52秒 | 4bit DiT を VRAM へ |
| VAE ロード | ~6秒 | |
| サンプリング(8 step) | ~15秒 | ~1.9秒/step |
| デコード | ~1秒 | |
| **モデルロード合計** | **~113秒(~76%)** | **毎回** CLI 呼び出しで発生 |

つまり sd.cpp は**ロード律速**: 各呼び出しの約¾が ~9GB の重みロード。実計算は
~30秒のみ。常駐サーバ(ComfyUI か sd.cpp の `sd-server`)がこれを償却する。

## 考察

- **ComfyUI の勝ちは限定的だが効く場面では巨大。** 1つのプロンプトで seed/step を
  振るなら、条件付けキャッシュで追加1枚はサンプラー分(~8〜18秒)のみ。他はこれに
  全く及ばない。
- **新プロンプトでは VRAM 制約で負ける。** int8 テキストエンコーダだけで 8.8GB —
  カード全体より大きい — ため新プロンプトごとにフル再ロード(~230秒)が発生し、
  sd.cpp のフル 4bit ラン**より遅く**なる。
- **sd.cpp は安定かつ堅牢。** プロンプトに関係なく毎回 ~150〜170秒、Edit も含めて
  クラッシュしない Vulkan 経路。キャッシュ崖も cuDNN 失敗も、この設定での #2 リスクも無い。

## 推奨

| やりたいこと | 使うべき経路 |
|---|---|
| **1つの**プロンプトで seed/step をインタラクティブ探索 | **ComfyUI ウォーム**(ノードUI) |
| **異なる**プロンプトのバッチ、または無人実行 | **sd.cpp**(Vulkan) |
| **画像編集(Edit)**、絶対に落ちては困る用途 | **sd.cpp**(Vulkan) |
| 高解像度 / 長時間(#2 リスク) | **sd.cpp**(Vulkan) |

既定は **sd.cpp + Vulkan**。1つのプロンプトを反復する時だけ ComfyUI ウォームを
使う。反復で sd.cpp を高速化したいなら `sd-server` を使い、1枚ごとの再ロードを
避けてモデルを常駐させる。
